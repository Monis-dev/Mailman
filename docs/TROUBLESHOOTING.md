# Troubleshooting

| Symptom | Why it happens | What to do |
|---|---|---|
| `401 Unauthorized` | Missing or incorrect `Authorization: Bearer <key>` header. | Confirm the key matches `RELAY_API_KEY` in `.env`. No trailing whitespace, no quotes copied in by accident. |
| `409 Conflict` on `POST /v1/jobs` | A job with this exact `Idempotency-Key` was already accepted in the last 24 hours. | This is the dedup working as intended. If you meant to send a new job, use a new key. If you meant to retry the same logical operation, this is correct behavior — check `GET /v1/jobs/:id` for its current status instead of resubmitting. |
| `400 Bad Request: Invalid target_url` | The SSRF guard rejected the URL — it resolved to a private IP, loopback, or a cloud metadata address. | Only public HTTP/HTTPS targets are allowed. If you're testing locally and need to hit `localhost`, run with `NODE_ENV` unset (non-production) — the loopback block only activates when `NODE_ENV=production`. |
| `429 Too Many Requests` | You exceeded `RATE_LIMIT_MAX` requests (default 10) in a 10-second window, per client IP. | Back off and respect the `Retry-After` header, or raise `RATE_LIMIT_MAX` if your traffic legitimately needs a higher ceiling. |
| Job stuck in `QUEUED`, webhook never arrives | Most commonly: the worker process isn't running. | Check that `node src/workers/mailman.js` is running and its logs show `Created group` or `Group already exists` on startup. If it's running, check for `CIRCUIT_SKIPPED` in its logs — see below. |
| `CIRCUIT_SKIPPED` in worker logs | The target domain failed 5 consecutive delivery attempts and the circuit breaker tripped to `OPEN` for 30 seconds. Jobs are parked, not lost. | Wait — delivery resumes automatically after the 30s cooldown. If it keeps re-tripping, the problem is on the destination end, not Mailman. |
| Redis `ECONNREFUSED` | The app can't reach Redis at `127.0.0.1:6379` (hardcoded — see `src/config/redis.js`). | Confirm the Redis container is up: `docker compose ps`. Restart with `docker compose up -d` if it's stopped. If Redis isn't on localhost, you'll need to edit `redis.js` directly. |
| Postgres connection errors on startup | Wrong or missing `HOST`/`PORT`/`USER`/`PASSWORD`/`DATABASE` in `.env`, or Postgres isn't running. | Check `docker compose ps`, confirm the values in `.env` match what's in `docker-compose.yml`, and that you ran `node src/config/migrate.js` after the database came up. |
| Job status is `DEAD_LETTER` | The job failed all 3 delivery attempts (bad response, timeout, or connection error each time). | Query `job_attempts` for that `job_id` to see the actual error and status code per attempt. Fix the destination or the payload, then call `POST /v1/jobs/:id/replay` to requeue it. |
| `POST /v1/jobs/:id/replay` returns `400 Only Dead Letter Jobs can be replayed` | You tried to replay a job that isn't in `DEAD_LETTER` status. | Only dead-lettered jobs are replayable. Check the job's current status first with `GET /v1/jobs/:id`. |
| Idempotency key seems "stuck" — legitimate retries keep getting `409` | If a request failed after the idempotency lock was acquired but before the job was fully written, the server should release the lock automatically. If you're seeing this anyway, the rollback path may not be reached in your version. | Confirm `server.js` deletes the `idempotency:<key>` Redis key in its catch block when a failure happens after the lock is set. If it doesn't, that's a bug to fix, not something to work around by changing keys. |
| Chaos suite fails on the SIGKILL/recovery proof | The worker takes longer than the poll window to recover the job, or a leftover circuit-breaker trip from a previous run is blocking delivery to `127.0.0.1`. | Don't rerun the suite immediately after a circuit-breaker proof — wait for the 30s cooldown, or clear `circuit:127.0.0.1:state` in Redis manually before rerunning. |
| Webhook signature verification fails on the receiver | Clock skew between sender and receiver beyond the tolerance window (default 300s), or the receiver is verifying against the wrong `secret`. | Confirm both sides use the same `WEBHOOK_SECRET`, and that server clocks are roughly in sync (NTP). |

If your issue isn't listed here, check `job_attempts` and the worker's logs first — both are structured JSON and usually name the exact failure. If it's a real bug rather than a config issue, open an issue with the relevant log lines and the job's `id`.
